# Архитектура проекта

Этот документ описывает внутреннее устройство библиотеки для разработчиков и контрибьюторов.

## 📐 Как это работает

```text
[Входной текст]
        │
        ▼
 [Нормализация и токенизация]
   └─ модуль: eng_to_ipa_hybrid.py
        │
        ▼
 [Поиск в словаре и морфологическая сегментация]
   └─ модуль: eng_to_ipa_hybrid.py
   └─ данные: en_dict.pkl + custom_vocabulary
        │
        ├── Не найдено ──► [Фонетические правила EN → IPA]
        │                        └─ модуль: rule_engine.py
        │                        └─ данные: eng_to_ipa_rules.pkl
        │                        │
        ▼ Найдено                ▼
  [Текст IPA] ◄──────────────────┘
```

## 🔄 Пайплайн обработки

### 1. Инициализация `Transcriber`

Все ресурсы загружаются сразу в конструкторе. Конструктор либо возвращает полностью готовый объект, либо выбрасывает исключение; промежуточного состояния не существует.

- **Правила English → IPA.** Загружаются из `data/eng_to_ipa_rules.pkl` и приводятся к кортежу `tuple[CompiledRule, ...]` (для быстрого хэширования в `lru_cache`).
- **Словарь.** `data/en_dict.pkl` десериализуется в `dict[str, str]` и сохраняется в `_en_dict`.
- **Объединенный словарь.** Собирается один раз: для ключей `custom_vocabulary` сохраняются исходный регистр и вариант в нижнем регистре (если он не переопределён явно), после чего словари объединяются (`{**_en_dict, **_custom_vocabulary}`). Если `custom_vocabulary` пуст, используется ссылка на `_en_dict` без копирования.
- **Длинные ключи (Long keys).** Заранее вычисленный `frozenset` ключей объединенного словаря длиной ≥ 4, используемый для поиска корней с конца незнакомых слов. Вычисляется один раз и сохраняется в `_long_keys`.

Если обязательный ресурс отсутствует, конструктор выбрасывает `FileNotFoundError`. Поврежденные данные могут вызвать исключение при чтении pickle.

### 2. Вызов `transcribe()`

`eng_to_ipa_hybrid.transcribe()` нормализует регистр (`CamelCase`, аббревиатуры), разбивает текст на токены, выделяет продуктивные суффиксы и словарные корни (справа налево с использованием `_long_keys`), подставляет IPA из словаря, а неизвестные сегменты транскрибирует через `rule_engine.transcribe()` (с LRU-кэшированием).

```text
│   ├── data/*.pkl              # Compiled runtime data

│   ├── transcriber.py          # Orchestrator (entry point)
│   ├── eng_to_ipa_hybrid.py    # Tokenization, dictionary lookup & segmentation
│   └── rule_engine.py          # Parallel non-destructive rule executor + LRU cache
├── .gitignore
├── LICENSE
├── README.md
├── THIRD_PARTY_LICENSES.md
└── pyproject.toml              # Metadata, build config
```

### Что где лежит

| Что | Где | Зачем |
|---|---|---|
| Исходный код | `src/crispy_ipa/` | src-layout — стандарт PyPA |
| Скомпилированные данные | `src/crispy_ipa/data/*.pkl` | Включаются в wheel при сборке |
| Исходники правил и словаря | `data_src/` | Удобны для ручного редактирования, не поставляются |
| Инструменты сборки | `scripts/` | Компиляция DSL и словаря перед релизом, не поставляются |
| Примеры и бенчмарки | `examples/` | Демо и замеры производительности, не поставляются |

## 🏗️ Архитектурные решения

### Почему класс `Transcriber`, а не функция?

Главная причина — жизненный цикл ресурсов. Словарь и данные правил загружаются один раз при инициализации и переиспользуются при каждом вызове `transcribe()`.

Обычная функция либо перезагружала бы ресурсы при каждом вызове, либо требовала скрытого глобального состояния. Класс делает загруженное состояние явным и позволяет разным экземплярам использовать разные пользовательские словари.

### Почему загрузка ресурсов при инициализации?

- **Быстрая транскрипция.** Загрузка правил и словаря во время инициализации гарантирует, что каждый вызов `transcribe()` будет быстрым. Пользователь не платит за I/O в середине обработки.
- **Простота внутри.** Ресурсы всегда на месте; `repr()` просто выводит их количество. Никаких состояний `Optional[...]`.
- **Предсказуемый жизненный цикл.** Весь ввод/вывод происходит ровно один раз при создании объекта.

Плата за это — около 60 мс на создание `Transcriber()` (загрузка pickle). Для TTS-пайплайнов и CLI-утилит это обычно не проблема.

### Зачем предвычислять `long_keys`?

`_split_word_from_end` нужен набор ключей словаря длиной ≥ 4 для поиска корней с конца незнакомых слов. Создание этого набора из 125 тысяч ключей при каждом вызове `transcribe()` стоило бы около 15 мс независимо от размера ввода. Вычисление один раз в `__init__` снижает затраты на вызов до ~0.07 мс (примерно в 200 раз быстрее).

### Почему исходные правила хранятся в `.py` с фонологическим DSL?

Макросы (словарь Python) и правила (многострочная строка в компактном фонологическом синтаксисе `L -> R / C`) хранятся в обычном Python-модуле `data_src/eng_to_ipa_rules.py`.

Это сочетает удобство импорта и подсветки в IDE с лаконичной записью контекстных правил без регулярных выражений в рантайме: скрипт сборки (`dsl_parser.py`) заранее разворачивает макросы и компилирует правила в кортежи для параллельного неразрушающего движка.
