# Архитектура проекта

Этот документ описывает внутреннее устройство библиотеки для разработчиков и контрибьюторов.

## 📐 Как это работает

```text
[Входной текст]
        │
        ▼
 [Нормализация и токенизация]
   └─ модуль: conversion.py
        │
        ▼
 [Поиск в словаре и морфологическая сегментация]
   └─ модуль: conversion.py
   └─ данные: data/en_dict.txt + custom_vocabulary
        │
        ├── Не найдено ──► [Фонетические правила EN → IPA]
        │                        └─ модуль: rule_engine.py
        │                        └─ данные: eng_to_ipa_rules.py
        │                        │
        ▼ Найдено                ▼
  [Текст IPA] ◄──────────────────┘
```

## 🔄 Пайплайн обработки

### 1. Импорт модуля `crispy_ipa.transcriber`

Ресурсы загружаются один раз при импорте модуля и сохраняются в модульных константах:

- **Правила English → IPA.** `dsl_parser.parse_rules()` разворачивает макросы и компилирует DSL-правила из `eng_to_ipa_rules.py` в `tuple[CompiledRule, ...]` — `_RULES`.
- **Словарь.** `dict_parser.parse_dict()` читает `data/en_dict.txt`, нормализует записи (срезает `/.../`, берёт первый вариант из списка через `,`) и возвращает `dict[str, str]` — `_DICT`.

### 2. Инициализация `Transcriber`

- **Объединенный словарь.** `_DICT` копируется, поверх накладывается `custom_vocabulary` (с lowercase-дубликатами ключей). Результат — `self._merged_vocabulary`.
- **Длинные ключи (Long keys).** Заранее вычисленный `frozenset` ключей объединенного словаря длиной ≥ 4, используемый для поиска корней с конца незнакомых слов — `self._long_keys`.

### 3. Вызов `transcribe()`

`conversion.to_ipa()` нормализует регистр (`CamelCase`, аббревиатуры), разбивает текст на токены, выделяет продуктивные суффиксы и словарные корни (справа налево с использованием `_long_keys`), подставляет IPA из словаря, а неизвестные сегменты транскрибирует через `rule_engine.transcribe()` (с LRU-кэшированием).

### Что где лежит

| Что | Где | Зачем |
|---|---|---|
| Исходный код | `src/crispy_ipa/` | src-layout — стандарт PyPA |
| Данные | `src/crispy_ipa/data/en_dict.txt` | Включаются в wheel при сборке |
| Исходники правил | `src/crispy_ipa/eng_to_ipa_rules.py` | Часть пакета, правится руками |
| Примеры и бенчмарки | `examples/` | Демо и замеры производительности, не поставляются |
| Инструменты разработки | `scripts/` | Не поставляются |

## 🏗️ Архитектурные решения

### Почему класс `Transcriber`, а не функция?

Базовые ресурсы — правила и словарь — общие для процесса и хранятся в модульных константах. Но `custom_vocabulary` у каждого экземпляра свой, и объединённый словарь вместе с `long_keys` вычисляется на экземпляр. Класс делает это состояние явным: разные экземпляры работают с разными пользовательскими словарями независимо, не мешая друг другу и не перезагружая базовые данные.

### Почему ресурсы загружаются при импорте?

- **Быстрая транскрипция.** К моменту первого вызова `transcribe()` всё уже готово. Пользователь не платит за I/O в середине обработки.
- **Простота внутри.** Ресурсы всегда на месте; `repr()` просто выводит их количество. Никаких состояний `Optional[...]`.
- **Предсказуемый жизненный цикл.** Весь ввод/вывод происходит ровно один раз при импорте модуля.

Плата — около 100 мс на `import crispy_ipa.transcriber` (парсинг DSL-правил и словаря). Для CLI-утилит и сервисов, где модуль импортируется один раз за процесс, это не проблема.

### Зачем предвычислять `long_keys`?

`_split_word_from_end` нужен набор ключей словаря длиной ≥ 4 для поиска корней с конца незнакомых слов. Создание этого набора из 125 тысяч ключей при каждом вызове `transcribe()` стоило бы около 15 мс независимо от размера ввода. Вычисление один раз в `__init__` снижает затраты на вызов до ~0.07 мс (примерно в 200 раз быстрее).

### Почему исходные правила хранятся в `.py` с фонологическим DSL?
с
Макросы (словарь Python) и правила (многострочная строка в компактном фонологическом синтаксисе `L -> R / C`) хранятся в обычном Python-модуле `eng_to_ipa_rules.py`.

Это сочетает удобство импорта и подсветки в IDE с лаконичной записью контекстных правил без регулярных выражений в рантайме: `dsl_parser.parse_rules()` разворачивает макросы и компилирует правила
в кортежи для `rule_engine.apply_rules()`.
